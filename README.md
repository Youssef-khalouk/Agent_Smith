## Description

     Agent Smith is an autonomous coding agent designed to solve programming challenges through iterative reasoning, code generation, execution, and observation.

     Unlike a traditional LLM-based application that generates a solution in a single response, Agent Smith implements an agentic framework in which a language model can explore a codebase, use tools, execute Python code in a controlled environment, inspect execution results, and refine its solution.

     The system follows a continuous feedback loop:

     Thought → Code → Observation → Iteration

     The project focuses on two programming benchmarks:

     MBPP (Mostly Basic Python Problems): Solving algorithmic programming problems by generating and testing Python functions.

     SWE-bench: Resolving real-world software issues by exploring repositories, modifying source code, executing tests, and producing Git patches.

     Another central component is the sandbox, which provides a controlled execution environment for code generated by the language model. The framework integrates the Model Context Protocol (MCP) to expose tools to the agent without coupling their implementation to the agent's reasoning loop.

     The main objectives are to build an autonomous coding framework that is modular, configurable, measurable, and designed with security and reproducibility in mind.

### Features

* Autonomous reasoning and code generation.

* Iterative execution and observation.

* Support for multiple LLM providers and models.

* Configurable agent iteration limits.

* Code extraction from different model response formats.

* MCP integration through standard input/output (stdio) and streamable HTTP.

* Dynamic discovery of MCP tools.

* Controlled execution of generated Python code.

* Configurable import and filesystem restrictions.

* Execution timeout and memory limits.

* File manipulation and code search tools.

* Automated test execution and patch generation.

* Usage tracking, including token consumption, latency, requests, and retries.

* MBPP and SWE-bench evaluation support.

* Benchmarking and comparison of language models.

## Tool Implementation Details

### The workspace abstraction

All tools are kitchen-blind: they never touch paths, containers, or "where am I" logic. Each tool asks a workspace — a waiter with one menu (`read_file_text`, `edit_file_text`, `list_directory_entries`, `search_files_for_pattern`, `search_function_or_class_definitions`, `find_name_references`, `run_command_in_folder`) — and formats the answer.

Two implementations exist behind the same interface:

- **LocalWorkspace** — files on the host (MBPP, and the host side of the mount)
- **DockerWorkspace** — composes LocalWorkspace (file tools, through the window) with ContainerManager.exec (commands, through the door)

The same tool code serves both worlds — verified by running the identical test suite against both workspaces (`tests/test_tools.py` locally, `tests/test_tools_with_docker.py` against a real container). Zero `if benchmark ==` branches exist inside tool code.

- `tools_common/workspace.py` — the workspaces, the exception family, the facts layer
- `tools_common/filesystem.py` — `read_file`, `edit_file`, `list_files`
- `tools_common/execution.py` — `run_command`, `get_patch`
- `tools_common/code_search.py` — `search_code`, `search_function_or_class_definition_in_code`, `find_references`

### The nine mandatory tools

| Tool | Contract | Output format |
|------|----------|---------------|
| `read_file(filepath, start_line, end_line)` | 1-based inclusive bounds, 200-line cap with a pagination hint telling the LLM the next `start_line` | `cat -n` style: `42: content` |
| `edit_file(filepath, old_str, new_str)` | exact string replace; refuses ambiguous matches and reports all line numbers; writes atomically (temp file + rename) | success message + a context window around the edit |
| `list_files(directory, pattern)` | glob patterns, sorted, `/` suffix on directories, 100-entry pagination via `offset` | one entry per line |
| `search_code(pattern, file_pattern)` | regex search, skips `.git` and binary files, 100-match pagination | `/absolute/path.py:42 content` |
| `search_function_or_class_definition_in_code(name)` | AST-based, so it survives syntax errors in the tree | same format |
| `find_references(name, filepath, line)` | word-boundary search across the workspace, excluding the definition line | same format |
| `run_command(command, workdir)` | returns stdout, stderr AND exit code; timeout kill with partial-output rescue; tail-kept output cap (failures print at the end) | labeled sections |
| `get_patch()` | runs `git -c core.fileMode=false diff` with intent-to-add (`git add -N`) so new files are included; permission-only changes excluded | the unified diff |
| `run_tests()` | executes the task's eval script through the door, 600s timeout, tail-kept output | labeled test output |

Optional parameters beyond the subject's contracts are exactly two: `offset` (pagination on list/search/find_references — required by the exam's cumulative token limits, since truncation hints reference it) and `end_line=None` on `read_file` (the same parameter with a clearer default). `search_function_or_class_definition_in_code` matches the subject's signature exactly — no additions. The subject permits additional tools and parameters ("you may implement any additional tools you consider useful"); these are the minimum the graded constraints forced, and nothing more.

### Tool design philosophy

**Facts in the workspace, messages in the tools.** The workspace layer raises raw facts (exceptions, counts, result packets); the tool layer translates them into text the LLM can act on. This keeps all LLM-facing behavior in one place and lets the workspace stay protocol-free and testable with zero MCP anywhere.

**Every error is a signpost.** Error messages tell the LLM what happened and what to try next ("file not found — call list_files to discover valid files"). Messages only reference tools and parameters that actually exist by their registered names.

**A failing command is a successful tool call.** A non-zero exit code is returned as a normal, labeled result — the agent needs test failures as information, not as tool errors. Only tool-level problems (timeout, command could not start) are errors.

**Output budgets by design.** Every tool caps its output (lines, matches, entries, characters) with a continuation hint where a continuation parameter exists — the same frugality that the exam's token limits (6k input for MBPP, 300k for SWE-bench) demand.

### Docker infrastructure

`ContainerManager` (`tools_common/docker_manager.py`) owns the container lifecycle with five abilities:

- **pull** — eager, at task start; instant no-op if the image exists
- **extract** — the ceremony: create a stopped blueprint container → copy `/testbed` to a host staging sibling folder → atomic rename onto the mount → discard the blueprint. Wipe-on-birth: a recycled task can never inherit stale state (the previous agent's edits die with the mount)
- **start** — bind mount + `sleep infinity` + git safe-directory pre-wiring; idempotent by construction: guard (already running? return) → reaper (sweep stale `agent-smith-*` orphans) → create
- **exec** — background thread + container-side GNU timeout self-kill (exit 124) + host-side deadline with partial-output rescue; returns the facts packet (stdout, stderr, exit_code, timed_out)
- **die** — force-remove, crash-guaranteed through context managers

Two invariants, both test-enforced: at most one `agent-smith-*` container alive at any moment (double-start returns the same container ID; a startup reaper sweeps orphans from previous runs), and `docker ps -a` is empty after every exit path — including deliberate crashes mid-task.

### The SWE-bench MCP server

`mcp_tools_swebench.py` (repository root, per the subject) exposes the nine tools, a resource (`task://context` — problem statement, instance id, hints) and a prompt (`fix_issue` — the agent workflow scaffold). Tools are bound closures: the server constructs one workspace and each tool's LLM-facing signature contains exactly the subject's parameters — the workspace is captured by the closure, never visible to the LLM (verified by schema inspection).

Configuration arrives per transport:

- **stdio (the graded path)** — environment variables at process birth: `SWEBENCH_IMAGE`, `SWEBENCH_MOUNT`, `SWEBENCH_EVAL_SCRIPT`, plus the task-context fields. Spawn order is the readiness guarantee: the ceremony completes before `MCP.run()` serves, so a client's `initialize` blocks until tools are live. No lifecycle machinery is needed — the connection closing IS the shutdown: stdin EOF ends `run()`, the with-block exits, the container dies. One task, one process.
- **streamable HTTP (remote-capable, beyond the subject's requirements)** — the server additionally offers runtime configuration: `POST /setup` (with force support for crash recovery), `GET /ready` (state polling: unconfigured → preparing → ready / failed with the actual error visible), `POST /shutdown` (the task-end signal). The task lifetime is decoupled from the server lifetime: ending a task releases the container, wipes the mount, and reopens setup — every new task gets a fresh world. An idle watchdog reclaims tasks whose client died silently (900 seconds without a tool call — a threshold that always exceeds the test-run timeout, so a patient agent is never reclaimed).

Both transports are served from one process: the FastMCP streamable app is mounted at `/mcp` inside a Starlette application that also carries the custom endpoints, with the MCP session manager kept alive through the application lifespan.

### Testing

The tools layer is covered by roughly 140 checks across four files:

- `tests/test_tools.py` — the local suite: every tool, every error path, exact output formats, pagination, path security, binary files, permission refusals (~65 checks)
- `tests/test_tools_with_docker.py` — the duel: the same tool calls against a real DockerWorkspace — the ceremony lifecycle (extraction, restart freshness, double-start identity, crash cleanup, the reaper), the door (timeouts with partial output, workdir security, the escape-containment proof: a command that escapes the workspace on LocalWorkspace is contained by the chamber on DockerWorkspace), file tools on the real repo, run_tests against the real eval script, and the patch round-trip (edit through the window → git through the door → patch applied to a fresh world)
- `tests/dummy_mcp_server.py` — a minimal two-tool MCP server over both transports; the rehearsal partner for the exam's unknown-MCP-server test

The architecture separates reasoning, execution, tool integration, and evaluation.

Main Components

1. Agent / Orchestrator

The orchestrator manages the agent lifecycle. It sends requests to the selected language model, processes responses, executes generated code through the sandbox, collects observations, and decides whether another iteration is necessary.

It also tracks usage metrics and enforces the applicable execution limits.

2. LLM Provider Layer

This component communicates with external language model APIs. It abstracts provider-specific details to make it possible to switch between models without redesigning the agent loop.

It is responsible for handling API requests, response parsing, errors, retries where permitted, token usage, and request latency.

3. Response Extraction

Language models may produce code in different formats. The extraction layer converts supported responses into executable Python code that the sandbox can process.

Supported formats include:

Python code blocks.

XML-style tool calls.

JSON/Hermes-style tool calls.

ReAct-style action descriptions.

The extraction layer must provide explicit feedback when it cannot extract valid code or when a response requires interpretation.

4. Sandbox

The sandbox is the execution boundary for LLM-generated Python code. It exposes dynamically discovered MCP tools as Python-callable functions and provides the final_answer() function.

It applies configurable restrictions to imports, filesystem access, execution time, and memory usage.

5. MCP Client and Servers

The MCP client runs as part of the sandbox integration layer. It connects to an external MCP server and exposes the server's available tools to generated Python code.

MCP servers operate independently from the sandbox and may provide file operations, code search, command execution, and testing capabilities.

6. Benchmark Agents

The MBPP and SWE-bench agents handle their respective task formats, execute the shared agentic workflow, and generate evaluation-compatible solution files.

### Agent loop:

The core of Agent Smith is an iterative Thought → Code → Observation loop.

Each iteration gives the language model an opportunity to inspect the problem, take an action, observe the result, and determine the next step.

1. Thought

The orchestrator sends the task description, the system prompt, previous observations, and the relevant interaction history to the language model.

The prompt explains the available tools, their parameters, and the expected problem-solving workflow.

The model determines what information it needs and generates a response containing code or a supported tool-call representation.

2. Code Extraction

The extraction layer identifies the executable action in the model's response.

If the model uses a supported non-Python format, the extraction layer converts it into equivalent Python function calls.

If no valid action can be extracted, the system should report the problem to the model rather than silently treating the response as successful execution.

3. Execution

The extracted code is executed inside the sandbox.

During execution, the code can use the Python functions exposed by the sandbox, including the MCP tool wrappers and final_answer().

MCP tool calls are handled by the connected MCP server.

4. Observation

The orchestrator collects the execution result, including relevant output and error information.

The result becomes feedback for the next model request.

The feedback should distinguish successful execution from failures, timeouts, missing code, truncated output, and other execution problems.

5. Iteration or Completion

If the task remains unresolved and execution limits permit, the orchestrator starts another iteration.

If the model submits a final solution through final_answer(), the sandbox captures the result and signals completion to the orchestrator.

For MBPP, the final result is Python solution code.

For SWE-bench, the final result is a Git patch representing the repository changes.

The agent terminates when a final answer is accepted, a configured limit is reached, or an unrecoverable error prevents further execution.

### Sandbox Design and Security

The sandbox executes code generated by a language model, which must be treated as untrusted input.

Its purpose is to limit the resources and capabilities available to that code while allowing the agent to solve programming tasks.

#### Configurable Restrictions

* Import restrictions

The sandbox uses an allowlist to determine which Python modules can be imported.

Only configured modules and permitted submodules should be available. Other imports are rejected by default.

#### Filesystem restrictions

* Filesystem operations are restricted to configured directories, such as:

     - /testbed

     - /tmp/agent

These paths represent the example defaults defined by the project specification. Actual permitted paths depend on the sandbox configuration and execution environment.

#### Network restrictions

Generated code must not be able to establish unauthorized inbound or outbound network connections.

Network isolation must be enforced by the execution environment rather than assumed to be guaranteed by removing a Python function or blocking an import alone.

#### Execution timeout

The sandbox limits how long generated Python code may execute.

When the configured timeout is exceeded, the execution must be terminated and the timeout reported to the agent.

#### Memory limits

The sandbox limits the memory available to generated code. Execution must be stopped or otherwise safely handled when the configured memory limit is exceeded.

#### Restricted builtins

Dangerous builtins and other potentially unsafe operations must be restricted to reduce the risk of privilege escalation or unauthorized access.

#### Configuration

Sandbox settings are managed through a Pydantic configuration model and a JSON configuration file.

The project specification defines the following example defaults:

##### Setting

Example default

* Maximum execution time: 30 seconds

* Maximum memory: 512 MB

* Allowed directories: /testbed, /tmp/agent

* Import policy: Configured allowlist

These are sandbox defaults, not the benchmark's overall time or token limits.

* Sandbox and MCP Boundaries

The sandbox and MCP server are separate security domains.

The sandbox restricts the execution of generated Python code. MCP tools execute through the connected server and may interact with files, repositories, Docker containers, or external processes.

Consequently, sandbox restrictions alone do not automatically constrain the actions performed by an MCP server. Tool implementations must apply their own appropriate validation and access controls.

The sandbox's execution timeout also does not automatically limit the duration of operations performed by an external MCP server.

Security note: Running generated Python code inside a process or using restricted builtins does not, by itself, guarantee strong isolation. Security guarantees depend on the actual isolation mechanisms implemented and tested by the project.
